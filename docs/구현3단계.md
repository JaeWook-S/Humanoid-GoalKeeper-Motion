# 구현 3단계: 랜덤 공 발사와 에피소드 초기화

작성일: 2026-11-01. 최근 수정: 2026-11-02. 대상 폴더: `Goalkeeper_mjlab`.
단계 번호는 구현·분석 이력을 위한 문서 이름이다. 학습 코드에 `Stage3SceneCfg` 같은 별도 장면을 만들지 않는다.

## 1. 이번 단계의 범위

**한 에피소드에 한 번의 랜덤 슛**을 발사한다. 로봇·공을 초기화하고, 땅볼 또는 뜬볼을 선택해 발사한 뒤,
로봇 접촉·골라인 통과·영역 이탈·시간 초과를 기록한다. 병렬 환경 중 에피소드가 끝난 환경만 새 슛으로 초기화한다.

```text
MJLab 기본 reset
→ 슛 조건 선택
→ 공의 위치·이동 속도·회전 속도 설정
→ 물리 계산마다 접촉·골라인 확인
→ 득점 / 영역 이탈 / 시간 초과
→ 해당 환경만 reset하고 다음 슛
```

이번 단계는 공을 막는 학습 정책을 만드는 단계가 아니다. 관측·action·보상·PPO는 후속 구현 대상이다.
로봇의 기본 자세는 사용자 요청에 따라 기존 `HOME_POSE`를 사용한다.
검사 실행기는 정책 대신 HOME 관절 목표각을 공급한다. 공을 막는 동작을 자동으로 만들어내는 제어기는 아직 없다.
이를 위해 `validation/shots.py`에서만 MJLab 기본 `JointPositionActionCfg`에 0 입력을 넣고,
기본 자세 offset을 더해 HOME 목표각을 명령한다. 4단계에서 사용할 정책 action을 미리 결정한 것은 아니다.

모터 설정과 속도별 토크 제한은 [구현2단계.md](구현2단계.md)의 구현을 재사용한다.
명령 지연과 부분 reset은 MJLab 기본 기능을 사용한다. 랜덤 발사와 골문 판정은 골키퍼 과제에 필요한 새 코드다.
참조 저장소 `booster_mjlab`은 **wirlwind 팀 코드**, 제조사 공식 코드는 **BoosterRobotics/booster_train**으로 구분한다.
이번 단계에서 로봇 모터값·발목 armature·PD gain·공과 골대의 접촉 물성을 새로 조정하지 않는다.

## 2. 실제 학습용과 검증용 파일

| 구분 | 파일 | 역할 |
| --- | --- | --- |
| 실제 학습 공통 | `tasks/goalkeeper/goalkeeper_env_cfg.py` | 공·골대·바닥·물리 기본값·슛 이벤트·접촉 센서·기록·종료 조건 |
| K1 학습 진입점 | `tasks/goalkeeper/config/k1/env_cfgs.py` | 공통 환경에 K1 로봇과 속도별 모터 제한 초기화를 연결 |
| 실제 학습 공통 | `tasks/goalkeeper/mdp/events.py` | `ShotCfg`, `ShotBatch`, 랜덤 조건 선택, 초기 속도 계산, 공 상태 쓰기 |
| 실제 학습 공통 | `tasks/goalkeeper/mdp/metrics.py` | 슛별 상태를 환경별로 보관하고 접촉·골라인 통과를 물리 스텝마다 기록 |
| 실제 학습 공통 | `tasks/goalkeeper/mdp/terminations.py` | 득점·영역 이탈·시간 초과를 MJLab 종료 조건으로 전달 |
| 검증 전용 | `validation/shots.py` | 실제 `ManagerBasedRlEnv`를 실행해 반복 슛을 검사하고 화면에 결과를 전달 |
| 화면·검사 진입점 | `scripts/inspect_scene.py`, `main.py` | `shots` 모드와 MuJoCo 화면·명령행 옵션·보고서 처리 |
| 자동 검증 | `tests/test_shots.py` | 샘플링·초기화·득점 판정·접촉·실제 환경 실행 검사 |
| 단독 실행 검증 | `tests/test_portability.py` | 원래 프로젝트·참조 폴더·네트워크 없이 슛 CLI 실행, 학습 설정과 검증 모듈의 의존성 분리 검사 |

학습 경로에서 `validation/`이나 `scripts/`를 import하지 않는다.
검사 실행기에서 학습 코드를 호출하므로, 검증용 발사 모델이나 검증용 골라인 계산식을 따로 만들지 않는다.
기존 `--mode motors`, `--mode geometry` 검사는 별도로 사용할 수 있다.

권장 읽는 순서는 다음과 같다.

1. `config/k1/env_cfgs.py`: 짧은 K1 로봇 연결부터 확인한다.
2. `goalkeeper_env_cfg.py`: 공·골대·물리·슛의 공통 환경 설정을 확인한다.
3. `events.py`의 `ShotCfg`, `sample_shots()`, `reset_ball_shot()`: 조절값과 발사 과정을 읽는다.
4. `metrics.py`: 날아가는 동안 어떤 상태를 계속 기록하는지 읽는다.
5. `terminations.py`: 어떤 상황에서 다음 에피소드로 넘어가는지 읽는다.
6. 화면·검사를 분석할 때 `validation/shots.py`, `inspect_scene.py`, `test_shots.py`를 읽는다.

### wirlwind와 같은 설정 구성

기존에는 장면·모터·물리 옵션을 하나의 긴 함수 인자로 받았다. 현재는 wirlwind의
`velocity_env_cfg.py → config/k1/env_cfgs.py`에 대응하는 두 파일로 구성한다.

```text
goalkeeper_env_cfg.py: make_goalkeeper_env_cfg()
  공·골대·바닥·물리 기본값·슛 구성
        ↓
config/k1/env_cfgs.py: goalkeeper_k1_env_cfg()
  K1 로봇·모터 초기화·환경 개수 연결
```

실제 학습과 검사는 `goalkeeper_k1_env_cfg()`를 호출한다. 공통 함수만 호출한 설정에는 아직 로봇이 없다.
K1 함수 인자는 `num_envs`, `ball`, `goal`, `shots`, `ball_position`, `goal_distance` 여섯 개다.
`physics_dt`, `solver`, `iterations`, `controllers`, 지연 등의 검사 옵션을 더 이상 인자로 받지 않는다.

| 바꿀 항목 | 현재 위치 |
| --- | --- |
| 공·골대·슛·배치·환경 개수 | `goalkeeper_k1_env_cfg()` 인자 |
| 물리 주기·정책 간격·솔버 반복 횟수 | `goalkeeper_env_cfg.py`의 `SimulationCfg`, `decimation` |
| 모터 물리값·PD·HOME·명령 지연 | `robots/k1/constants.py` |
| 특정 실험의 seed | 반환된 `cfg.seed` |
| 검사에서만 바꾸는 모터·물리 조건 | CLI/테스트에서 반환된 `cfg`나 `get_k1_robot_cfg()`를 직접 수정 |

solver는 wirlwind처럼 MJLab 기본 Newton을 사용해 명시하지 않는다.
물리 200 Hz·정책 50 Hz, 모터 수치, 공·골대의 접촉 물리는 기존과 같다.
`cone="elliptic"`은 기존 땅볼 구름 마찰을 위해 유지하며 wirlwind의 기본값과 다른 항목이다.

### 공통 파일의 항목별 배치

파일을 분리하는 것과 항목을 읽기 쉽게 배치하는 것은 별개다. 공통 파일 내부도
wirlwind처럼 항목별 변수로 설정을 정의하고 맨 아래에서 한 번에 조립하도록 구성했다.
환경의 전체 연결을 확인할 때는 `make_goalkeeper_env_cfg()`의 마지막 `return`부터 읽는다.

```python
return ManagerBasedRlEnvCfg(
    scene=SceneCfg(
        terrain=TerrainEntityCfg(...),
        entities={...},
        sensors=sensors,
        num_envs=1,
        env_spacing=4.0,
        spec_fn=...,
    ),
    observations=observations,
    actions=actions,
    commands=commands,
    events=events,
    rewards=rewards,
    terminations=terminations,
    curriculum=curriculum,
    metrics=metrics,
    viewer=ViewerConfig(),
    sim=SimulationCfg(...),
    decimation=4,
    episode_length_s=episode_length_s,
    # seed는 실행하는 쪽에서 지정한다.
)
```

위 코드는 구성 형태를 보여 주기 위한 축약이며 실제 파일에는 자산·센서·이벤트 설정을 풀어 적었다.
공통 함수 안에서 먼저 `cfg`를 만든 뒤 `cfg.events`, `cfg.metrics`, `cfg.terminations`를
여러 위치에서 수정하는 후처리는 제거했다. K1 파일에서 모델별 로봇을 연결하는 구성은 유지한다.
복잡한 중첩 호출도 한 인자씩 줄을 나눠 각 필드가 어디에 속하는지 보이도록 했다.

관측·action·commands·보상·자동 커리큘럼은 아직 구현 전이므로 해당 dict는 비어 있다.
이를 조립부에도 명시해 현재 연결된 항목과 후속 구현할 항목을 함께 확인할 수 있다.
`events`를 직접 넘기면 MJLab 기본 이벤트 dict를 대체하므로, 기본 함수
`reset_scene_to_default`를 첫 이벤트로 명시했다. 이 함수의 환경별 초기화 동작은 그대로 사용한다.

## 3. 좌표·단위와 높이의 의미

현재 장면에서는 로봇 앞이 `+X`, 로봇 왼쪽이 `+Y`, 위쪽이 `+Z`다.
공은 로봇 앞의 양의 X 위치에서 출발해, 뒤쪽 음의 X에 있는 골문으로 향한다.
길이는 m, 시간은 s, 이동 속도는 m/s, 회전 속도는 rad/s다.

### 현재 로봇~골대 거리와 변경 위치

거리는 **로봇 기준점 `x=0`에서 뒤쪽 골라인까지의 수평 거리**다. 로봇 표면과 기둥 사이의 최단 거리가 아니다.

| 실행 경로 | 현재 기본 거리 | 설정 위치 |
| --- | --- | --- |
| `main.py --mode shots` | **0.5 m, 뒤쪽 50 cm** | `scripts/inspect_scene.py`의 `--goal-distance`, `default=0.5` |
| Python에서 `goalkeeper_k1_env_cfg()` 직접 호출 | **0.75 m, 뒤쪽 75 cm** | `config/k1/env_cfgs.py`의 `goal_distance=0.75` |
| 공통 장면의 실제 배치 | `goal_distance`로 받은 값 | `goalkeeper_env_cfg.py`의 골대 `pos=(-goal_distance, 0.0, 0.0)` |

CLI는 자신의 기본값도 명시적으로 환경 함수에 전달하므로 `main.py` 실행에서는 CLI 값이 우선한다.
현재 수치를 임의로 통일하지 않았다. 예를 들어 `Robocup-RL` 폴더에서 다음처럼 실행하면 0.5 m가 된다.

```bash
Goalkeeper_mjlab/.venv/bin/python Goalkeeper_mjlab/main.py --mode shots --goal-distance 0.5
```

같은 `goal_distance`를 골대 배치·발사 목표점·골라인 판정에 전달하므로 세 곳을 따로 수정할 필요가 없다.

공의 위치는 **공 중심의 위치**다. 반지름이 0.1 m인 공을 바닥에 놓으면 중심 높이는 0.1 m다.
중심 높이를 0으로 지정하면 공의 아래 절반이 바닥 안에 들어가므로 땅볼도 높이를 반지름으로 설정한다.

`발사 높이`는 출발할 때 공 중심의 높이이고, `목표 높이`는 골라인에 도착할 때 목표로 하는 공 중심의 높이다.
둘은 서로 다르다. 낮은 곳에서 출발해 위쪽으로 향하는 공도 만들 수 있다.

병렬 환경에는 각자의 `env_origins`가 있다. 샘플러는 로봇 주변의 **환경 내부 좌표**를 계산하고,
실제 엔진에 위치를 쓸 때만 환경 원점을 한 번 더한다. 속도에는 위치 원점을 더하지 않는다.
따라서 0번 환경이 원점, 1번 환경이 몇 m 떨어진 곳에 배치되어도 같은 슛 조건을 사용할 수 있다.

## 4. ShotCfg: 무엇을 어디서 조절하는가

슛 설정은 `mdp/events.py`의 `ShotCfg`에 모았다. 여러 개의 장면 설정 파일이나 단계별 설정 wrapper로 나누지 않는다.

| 필드 | 기본값 | 의미 |
| --- | --- | --- |
| `ground_probability` | `0.5` | 땅볼을 선택할 확률. 0은 모두 뜬볼, 1은 모두 땅볼 |
| `launch_distance` | `(1.0, 3.0)` | 로봇 앞 출발 X 위치 범위, m |
| `launch_y` | `(-2.0, 2.0)` | 출발 좌우 위치 범위, m |
| `air_launch_height` | `(0.2, 0.6)` | 뜬볼의 출발 중심 높이 범위, m |
| `speed` | `(3.0, 8.0)` | 출발 이동 속도의 크기 범위, m/s |
| `target_y_fraction` | `(-0.85, 0.85)` | 공이 기둥과 겹치지 않는 골문 반폭에 대한 목표 좌우 비율 |
| `air_target_height_fraction` | `(0.05, 0.85)` | 공이 바닥·가로대와 겹치지 않는 높이 구간에 대한 목표 높이 비율 |
| `max_sampling_attempts` | `128` | 도달 불가능한 조합을 다시 선택할 수 있는 최대 횟수 |
| `episode_timeout_s` | `3.0` | 한 슛을 관찰하는 최대 시간, s |
| `out_margin` | `2.0` | 슛 검사 영역 바깥에 두는 여유 거리, m |

출발 거리 1.5 m는 골라인까지 1.5 m라는 뜻이 아니다.
골라인이 `x=-0.75 m`이면 출발점 `x=1.5 m`에서 골라인까지 정면 거리는 2.25 m다.

골문 좌우 목표 비율은 `-1`이 사용할 수 있는 한쪽 끝, `0`이 중앙, `+1`이 반대쪽 끝이다.
좌우 부호는 장면 Y 방향을 따른다. 사용할 수 있는 반폭은 `골문 안쪽 폭 / 2 - 공 반지름`이다.
기둥 중심이나 골대 바깥 폭을 그대로 목표 범위로 쓰지 않는다.

목표 높이 비율은 공 중심이 바닥에 닿는 높이 `반지름`부터,
가로대에 겹치지 않는 높이 `골문 안쪽 높이 - 반지름`까지의 구간에서 고른다.
0은 바닥에 놓인 공의 중심 높이, 1은 가로대 바로 아래에 들어갈 수 있는 중심 높이다.
이렇게 비율을 사용하면 `small/mid/large` 골대와 공 크기가 달라져도 골문 안쪽의 유효 범위에 맞춘다.

```python
from goalkeeper_mjlab.tasks.goalkeeper.config.k1.env_cfgs import goalkeeper_k1_env_cfg
from goalkeeper_mjlab.tasks.goalkeeper.mdp.events import ShotCfg

shots = ShotCfg(
    ground_probability=0.8,          # 80% 땅볼, 20% 뜬볼
    launch_distance=(1.5, 2.5),    # 로봇 앞 1.5~2.5 m
    launch_y=(-0.5, 0.5),          # 출발점을 정면 근처로 제한
    speed=(3.0, 6.0),              # 출발 속도 3~6 m/s
    target_y_fraction=(-0.4, 0.4), # 골문 중앙 쪽을 주로 향하게 함
)
cfg = goalkeeper_k1_env_cfg(num_envs=128, shots=shots)
cfg.seed = 0  # seed는 반환된 MJLab 기본 설정에서 변경한다.
```

위 수치는 사용법을 보여주는 예시다. 최종 학습 난이도나 실제 슈터 속도를 측정해 확정한 값은 아니다.
`goalkeeper_k1_env_cfg()`는 기본적으로 `shots=ShotCfg()`를 사용한다.
인자를 생략해도 발사·접촉 센서·기록·종료 기능이 항상 연결되며 슛을 끄는 `None` 모드는 없다.
범위를 바꾸려면 `shots=ShotCfg(...)`를 전달한다. 호출마다 설정을 복사하므로
한 환경 설정의 커리큘럼 값을 수정해도 다음에 만드는 환경의 기본 분포가 바뀌지 않는다.
기존 형상·모터 검사에서 필요 없는 추가 센서는 각 검증 도구가 복사한 장면에서 제외한다.

## 5. 공을 어떻게 발사하는가

### 선택 순서

`sample_shots()`는 슛 종류 → 출발 위치 → 골문 목표 지점 → 속도를 선택하고,
그 조건을 만족하는 초기 이동·회전 속도를 계산한다.
방향까지 서로 관계없는 난수로 고르면 공이 골문 반대쪽으로 갈 수 있으므로 목표 지점에서 방향을 계산한다.

발사는 한 번 힘을 가해서 속도가 얼마나 나오는지 기다리는 방식 대신,
**시작 순간 공의 속도를 직접 설정**한다. 이후 이동·중력·마찰·충돌은 실제 MuJoCo 물리가 계산한다.
매 프레임 공을 목표점 쪽으로 강제로 옮기거나 속도를 계속 덮어쓰는 방식이 아니다.

### 땅볼

땅볼은 중심 높이를 공 반지름으로 정하고 수평 방향으로 발사한다.
공은 이동하면서 함께 굴러야 하므로 이동 속도에 맞는 회전 속도도 설정한다.
예를 들어 바퀴가 바닥에서 굴러갈 때 이동과 회전이 함께 일어나는 것과 같은 관계다.

속도와 반지름이 같다면 큰 공보다 작은 공이 더 빨리 회전해야 같은 거리를 굴러간다.
이 관계를 `이동 속도 / 반지름`으로 계산한다. 처음부터 바닥에서 과도하게 미끄러지는 상태를 줄이기 위한 설정이다.

공은 바닥 저항 때문에 점점 느려진다. 너무 느려서 골문 전에 멈출 것으로 예상되는 조건은 다시 고른다.
이 검사는 기존 `BALL_ROLLING_RESISTANCE=0.060`을 이용한 평지의 근사 계산이다.
실제 궤적을 정답에 맞춰 수정하지 않으며 접촉 솔버·공의 회전·다른 물체와의 충돌에 따라 실제 도달 위치와 시간이 달라질 수 있다.

### 뜬볼

뜬볼은 출발점과 목표점 사이에서 중력 때문에 내려오는 양을 고려해 초기 속도를 계산한다.
같은 목적지라도 높이 던지는 경로와 낮게 보내는 경로가 가능한 경우가 있다.
현재는 골키퍼를 향한 슛에 맞춰 **낮은 궤적**을 선택한다.

설정한 속도가 너무 느려 선택한 거리·높이에 도달할 수 없으면 해당 조건을 다시 고른다.
최대 재선택 횟수 안에 가능한 조건을 만들지 못하면 오류로 알린다.
유효한 슛을 만들려면 사용자가 속도·거리·높이 범위를 조정해야 한다.

이 계산은 중력을 고려한 기본 포물선이다. 공기 저항이나 공 회전에 의한 휘어짐은 구현하지 않았다.
공이 로봇·기둥·바닥에 부딪힌 이후에는 실제 접촉 물리가 궤적을 바꾼다.

각 구간에서 난수를 선택하지만 도달 불가능한 조합은 제외하므로,
최종 발사 데이터 전체가 모든 변수를 서로 독립적으로 균일하게 포함하는 것은 아니다.
발사 시 설정 범위와 도달 가능한 조합으로 초기 속도를 계산하지만, 목표점의 별도 기록 사본은 유지하지 않는다.

### 계산 결과의 형태

`ShotBatch`는 실제 엔진 입력인 `position`, `linear_velocity`, `angular_velocity`만 전달한다.
모두 `[N, 3]` 형태다. 목표점·종류·속력은 발사 계산 안에서만 필요하므로 결과에 복사해 두지 않는다.
속력은 필요하면 이동 속도 벡터의 크기로 읽을 수 있다. 현재 소비자가 없는 예상 비행 시간 계산도 제거했다.

`reset_ball_shot()`에서 실제 엔진에 쓰는 공의 `root_state`는 환경마다 13개 값이다.

```text
[위치 x,y,z | 방향 w,x,y,z | 이동 속도 x,y,z | 회전 속도 x,y,z]
```

위치에만 환경 원점을 더하고 초기 방향은 단위 quaternion `(1, 0, 0, 0)`으로 둔다.
공의 현재 방향과 얼마나 빨리 도는지는 다른 값이므로, 초기 방향을 같게 두어도 땅볼의 회전 속도는 따로 지정할 수 있다.

## 6. MJLab 기본 초기화와 환경별 상태

기본 `reset_scene_to_default` 이벤트가 로봇·공·골대 상태를 복원한 뒤,
`reset_ball_shot()`이 선택된 환경의 공 위치·회전·이동 속도·회전 속도를 새 슛으로 설정한다.
모터 명령 지연 버퍼와 센서의 부분 reset은 MJLab이 처리한다.

### 시작할 때의 움찔거림과 HOME 목표각 정렬

K1의 `robot_joint_targets` reset 이벤트에서 `reset_robot_joint_targets()`를 호출해
첫 제어 명령을 HOME 목표각으로 맞춘다. 이 연결은 wirlwind 참조 구성에 추가한 부분이다.

MJLab의 `Entity.reset()`은 모터 목표각을 0으로 지운다. 기본 장면 reset은 실제 관절각을 HOME으로
복원하지만 모터 목표각까지 복원하지는 않는다. 이후 `env.reset()` 안에서 첫 제어 명령을 쓰므로,
아무 연결 없이 실행하면 0 rad가 기본 지연 버퍼의 첫 값으로 들어갈 수 있다.

수정 전 실제 실행에서는 왼쪽 무릎의 자세가 0.8 rad, 목표 명령은 0 rad였으며 초기 토크가
-64 N·m로 측정됐다. 처음 몇 물리 스텝의 지연된 명령도 0↔0.8 rad 사이를 바꿔 로봇이 움찔했다.
이를 단순한 중력 적응이나 정상적인 작은 진동으로 해석하면 안 된다.

수정한 흐름은 다음과 같다.

```text
MJLab Scene.reset: 모터 목표각과 지연 상태 초기화
→ 기본 reset_scene_to_default: 실제 관절각을 HOME으로 복원
→ 발사 이벤트: 새 공 설정
→ robot_joint_targets 이벤트: 모터 목표각도 HOME으로 지정
→ 첫 제어 명령 쓰기: 기본 DelayBuffer가 첫 HOME 명령을 자동으로 이력에 채움
```

이벤트에서는 기본 `set_joint_position_target()`만 사용한다. 지연 버퍼를 직접 수정하지 않고,
지연을 끄거나 사전 물리 진행으로 문제를 숨기지 않는다. 초기 생성·R 키·자동 reset에 모두 적용하며
선택한 환경의 목표각만 복원하므로 진행 중인 환경의 명령은 유지한다.
첫 명령 이후 최대 지연보다 긴 12개 물리 스텝에서도 실제 엔진 명령이 HOME으로 유지되는지 검사한다.

이는 잘못된 0 rad 명령을 제거하는 수정이다. 발바닥 초기 여유 1 mm에서 중력과 접촉에 적응하는
작은 움직임, 고정 PD만으로 HOME 자세의 균형을 유지하는 문제는 별도로 남을 수 있다.
사용자가 변경한 머리 stiffness=10, damping=1.2와 기존 모터 물리값은 이 수정에서 변경하지 않았다.

### 환경별 진행 상태와 기록

예를 들어 `env_ids=[0, 2]`를 reset하면 0번과 2번 환경만 새 슛을 받는다.
1번 환경의 공 위치·속도·접촉 기록·진행 시간은 그대로 유지되어야 한다.
전체 환경을 매번 reset하거나, 이전 에피소드의 접촉 사실이 다음 에피소드에 남아서는 안 된다.

고정한 MJLab 버전은 `scene.reset → reset 이벤트 → metrics.reset` 순서로 실행한다.
발사 이벤트의 `begin_shots()`에서 선택한 환경의 판정 상태·직전 위치·종료 범위를 초기화한다.
`ShotTracker`에 별도 `reset()`을 구현하지 않고, 기본 `ManagerTermBase.reset()`을 그대로 사용한다.
이미 새로 만든 상태를 뒤에서 다시 지우지 않는다. MJLab의 reset 자체를 대체한 것은 아니다.

자동 reset은 `env.step()`이 호출자에게 돌아오기 전에 실행될 수 있다.
이전 결과를 복사하는 `last_result`는 제거했다. 종료 여부는 `env.step()`이 반환하는
`terminated`·`truncated`로 확인하고, 종료된 에피소드 통계는 기본 `info["log"]`에서 읽는다.
예를 들어 `Episode_Termination/goal`은 이번 reset 묶음에서 goal 조건이 참인 환경 수다.
이는 기본 매니저의 집계이며 슛별 상세 보고서가 아니다.
연속 발사 도구 `ShotSimulation`은 MJLab 기본 자동 reset을 사용하므로 `auto_reset=True`를 요구한다.

학습 중 필요한 상태만 환경별 Torch tensor로 보관한다. 검사기에도 상세 슛 로그 리스트를 쌓지 않는다.
난수 seed는 환경 생성 시 설정하며 reset 때마다 같은 seed를 다시 설정하지 않는다.
같은 seed와 실행 조건에서는 재현할 수 있지만 CPU와 CUDA 사이의 난수열·접촉 결과가 완전히 같다는 보장은 없다.

## 7. 접촉 기록과 골라인 판정

### 접촉은 기본 ContactSensor 사용

MJLab의 기본 `ContactSensor`에서 로봇과 공 사이의 접촉을 읽는다.
바닥·골대 접촉을 로봇 접촉으로 잘못 세지 않도록 접촉 상대를 공으로 제한한다.
`fields=("found",)`로 접촉 여부만 읽고, `touched`에 이번 슛의 접촉 사실을 기억한다.
접촉 힘·최초 시각·부위별 누적 기록은 현재 학습 판정에 쓰지 않아 수집·보관하지 않는다.

`현재 접촉 중`과 `이번 에피소드에서 한 번이라도 접촉함`은 다르다.
손에 맞고 튀어나간 공은 다음 순간 손과 떨어져 있어도 이번 에피소드의 접촉 기록은 남아야 한다.

**공 접촉은 선방 성공과 같은 뜻이 아니다.** 로봇에 맞은 뒤 골문으로 들어갈 수 있다.
그래서 첫 로봇 접촉만으로 에피소드를 끝내지 않고, 이후 득점 여부도 계속 확인한다.

### 정책 주기가 아닌 물리 계산마다 확인

기본 물리 시간 간격은 0.005 s이므로 200 Hz, `decimation=4`이므로 정책 주기는 50 Hz다.
정책이 한 번 실행되는 동안 물리는 네 번 진행된다.
짧게 발생했다 사라지는 접촉이나 빠른 공의 골라인 통과를 잡기 위해 물리 스텝별 기록을 사용한다.

MJLab의 기본 물리 스텝별 metrics 실행 지점에 연결한다.
공의 통과 위치는 현재 적분된 공 상태를 기준으로 읽고, 프레임 간 이동 구간을 사용한다.
화면을 그리기 위한 CPU `MjData`를 판정의 원본으로 사용하지 않는다.

공 위치와 접촉 데이터의 시간 기준도 구분한다.
공의 자유 관절 `qpos`는 이번 적분을 마친 위치이고, 엔진 접촉 센서는 그 적분에 사용한 접촉 상태를 나타낸다.
둘 다 물리 스텝마다 읽으므로 정책 실행 사이에 잠깐 생긴 접촉도 `touched`에 남는다.

### 공 전체가 넘어간 경우만 득점

현재 배치에서 골문 앞은 X가 큰 쪽, 골문 뒤는 X가 작은 쪽이다.
공 중심이 골라인을 조금 넘어갔어도 공의 앞부분이 아직 선 위에 있으면 득점 처리하지 않는다.
공 반지름을 함께 고려해 **공 전체가 골라인 뒤로 넘어가는 시점**을 확인한다.

이전 위치와 현재 위치 사이에서 통과 시점을 계산하고, 그때의 좌우·높이가 골문 안쪽에 들어가는지 검사한다.
공 크기 때문에 기둥·가로대와 겹치지 않도록 중심이 들어갈 수 있는 범위에서 판정한다.
골문 밖이나 가로대 위를 통과한 공, 뒤에서 앞으로 움직이는 공은 득점이 아니다.
득점 플래그는 에피소드 동안 유지하므로 같은 공을 여러 번 득점으로 기록하지 않는다.

검사 시점은 두 개다. **공 중심이 골라인을 지날 때** 실제로 골문 안으로 들어갔는지를 기록하고,
**공 전체가 골라인을 지날 때**도 유효 범위 안인지 확인한 뒤 득점을 확정한다.
공 전체가 넘어간 마지막 위치만 보면 기둥 바깥에서 대각선으로 들어온 공을 잘못 인정할 수 있기 때문이다.
중심이 먼저 골문 안으로 진입했다는 사실은 `entered_opening`에 보관하고, 선 앞으로 튕겨 나오면 다시 확인한다.

땅볼이 지나가는 바닥 쪽 높이에는 1 mm의 판정 여유 `GOAL_FLOOR_TOLERANCE=0.001`을 둔다.
기본 4호 공과 현재 접촉 설정의 실제 2·3 m/s 땅볼 실행에서 공과 바닥이 약간 겹쳐 공 중심 높이가 반지름보다 내려가는 현상을 확인했다.
검사 중 관찰한 최대 바닥 침투는 약 0.53 mm였고, 선을 지날 때 약 0.09~0.23 mm의 겹침만 있어도
완전히 엄격한 높이 비교에서는 정상 땅볼을 득점으로 인정하지 못했다.
이 여유는 **득점 판정의 바닥 높이 비교에만** 적용한다. 공 반지름·바닥 높이·마찰·접촉 물성을 바꾸지 않으며,
옆 기둥과 가로대의 공 크기 여유를 줄이지 않는다. 실제 땅볼을 굴리는 회귀 검사로 이 처리를 확인한다.

골라인 판정은 득점을 관찰하는 코드다. 눈에 보이지 않는 벽이나 골문을 막는 충돌체를 추가하지 않는다.

## 8. 최소 종료 조건과 이후 커리큘럼

3단계의 종료 조건은 득점, 검사 영역 이탈, 제한 시간 초과다.
시간 초과는 결과를 더 기다리지 않고 다음 슛으로 넘어가기 위한 조건이다.
공이 골문 밖으로 갔다고 모두 선방으로 부르거나, 시간 초과를 자동으로 선방 보상으로 바꾸지는 않는다.
본격적인 선방 성공 기준과 보상은 후속 학습 단계에서 설계한다.

커리큘럼은 **같은 ShotCfg의 범위와 확률을 조절하는 방식**으로 연결할 수 있다.

| 예시 순서 | 바꾸는 값 |
| --- | --- |
| 느린 중앙 땅볼 | 땅볼 확률을 높이고 속도·출발 좌우·목표 좌우 범위를 좁힘 |
| 좌우 땅볼 | 목표 좌우와 출발 좌우 범위를 확대 |
| 뜬볼 혼합 | 땅볼 확률을 낮추고 목표 높이 범위를 사용 |
| 다양한 슛 | 속도·거리·높이 범위를 점진적으로 확대 |

이는 난이도 구성을 설명하는 예시이며 자동 승급 규칙을 구현한 것은 아니다.
성공률을 보고 자동으로 난이도를 바꾸는 기준은 이후 학습에서 연결한다.
새 설정은 **다음 reset에서 생성하는 슛부터 적용**한다. 이미 날아가는 공을 중간에 순간이동시키지 않는다.
발사 이벤트와 기록 관리자는 MJLab 내부에서 설정을 각각 복사할 수 있으므로,
슛을 시작할 때 제한 시간과 검사 영역도 환경별 버퍼에 보관한다.
나중에 설정을 바꾸어도 이미 진행 중인 다른 환경의 제한 시간·검사 영역이 갑자기 바뀌지 않게 하기 위해서다.

이미 생성한 환경의 분포를 바꿀 때는 처음 만들었던 `cfg` 변수 대신 **실행 중인 발사 이벤트의 설정**을 바꾼다.
MJLab 매니저가 설정을 복사하기 때문이다.

```python
from dataclasses import replace

# env는 실제 ManagerBasedRlEnv다. 검사기에서는 simulation.env에 해당한다.
term = env.event_manager.get_term_cfg("launch_ball")
term.params["shot_cfg"] = replace(
    term.params["shot_cfg"],
    ground_probability=0.3,  # 다음 슛부터 뜬볼 비중 확대
    speed=(4.0, 8.0),
)
# 여기서는 공을 직접 움직이지 않는다. 각 환경의 다음 reset에서 새 설정을 읽는다.
```

## 9. 구현 중 필요해서 보강한 부분

| 위치 | 추가·보강한 내용 | 필요한 이유 |
| --- | --- | --- |
| `metrics.py: GOAL_FLOOR_TOLERANCE` | 바닥 쪽 득점 높이에만 1 mm 허용 오차 | 실제 접촉 솔버의 미세한 바닥 침투 때문에 정상 땅볼을 놓치는 문제를 막기 위해 |
| `metrics.py: entered_opening` | 중심의 골라인 진입과 공 전체 통과를 함께 확인 | 골문 밖에서 대각선으로 들어오는 경로를 잘못 득점 처리하지 않기 위해 |
| `metrics.py: begin_shots()` | 발사 당시 제한 시간·영역을 환경별로 보관 | 커리큘럼 변경이 이미 진행 중인 다른 환경까지 바꾸지 않게 하기 위해 |
| `metrics.py: ball_qpos_adr` | 이름으로 공의 자유 관절 주소를 찾고 최신 `qpos`에서 위치 읽기 | 물리 적분 직후 한 스텝 전 상태일 수 있는 `xpos`로 빠른 통과를 놓치지 않기 위해 |
| `validation/shots.py` | 기본 위치 action으로 HOME 입력 제공 | 정책 action 구현 전에도 실제 `ManagerBasedRlEnv`의 공 발사 흐름을 검증하기 위해 |
| `mdp/events.py: reset_robot_joint_targets()`, K1 `robot_joint_targets` 이벤트 | 첫 제어 명령을 HOME 목표각으로 정렬 | reset 시 0 rad가 지연 이력에 들어가 시작·에피소드 전환 때 움찔하는 오류를 막기 위해 |

이 보강들은 새로운 모터 물리 모델이나 별도 reset 시스템을 추가한 것이 아니다.
득점·기록은 실제 학습 공통 코드이고, HOME 검사 입력과 보고서는 검증 도구에만 있다.

### 사용하지 않는 기록 정리

학습 판정·reset·발사·화면 실행과 전체 참조를 확인한 뒤 다음을 제거했다.
나중에 필요할 수도 있다는 이유로 아직 사용하지 않는 보상용 기록을 미리 쌓지 않는다.

| 제거한 부분 | 이유·현재 방식 |
| --- | --- |
| `shot_id`, `active`, `goal_count` | 슛 번호·대기 상태·중복 횟수 기록은 사용하지 않음. 매 reset에 발사하고 `goal`로 이번 슛 득점을 기억 |
| 발사 위치·목표·속도·종류 사본, 예상 비행 시간 | 현재 공 상태는 엔진에 있음. 목표점·종류는 발사 함수 안에서만 사용하고, 예상 시간 계산은 제거 |
| `goal_time`, `first_contact_time`, `first_contact_body`, `contact_body_mask`, `peak_contact_force` | 현재 보상·종료 조건에서 사용하지 않는 상세 기록 |
| `last_result`, `has_last_result` | 종료 결과를 중복 복사함. 기본 step 반환값과 매니저 통계를 사용 |
| 검사기의 `records`와 슛별 JSON 목록 | 상세 로그를 누적할 필요 없음. 완료 개수만 계산 |
| `ShotTracker.reset()`의 빈 재정의 | 기본 `ManagerTermBase.reset()`이 동일하게 아무 작업도 하지 않음 |
| 모터의 미사용 상수·전역 `K1_ARTICULATION`·공식 gain 비교 함수 | 실제 참조가 없음. 설정은 기존 factory로 생성하고, 출처 자료는 JSON에 보존 |

`ShotTracker`에 남은 환경별 상태는 다음과 같다.

| 상태 | 학습 시 필요한 이유 |
| --- | --- |
| `elapsed` | 슛 제한 시간 판정 |
| `previous_position` | 빠른 공이 두 물리 스텝 사이에서 골라인을 넘었는지 확인 |
| `goal`, `entered_opening` | 골문 안쪽 진입과 공 전체 통과 판정 |
| `touched` | 잠깐 접촉한 사실도 이번 슛이 끝날 때까지 유지 |
| `out`, `timeout` | 종료 조건과 기본 에피소드 통계 |
| `timeout_limit`, `out_x_min/max`, `out_y_max`, `out_z_max` | 다음 reset부터 바뀌는 커리큘럼을 위해 발사 당시의 종료 범위 유지 |

위 상태의 초기화 대상은 MJLab이 전달한 환경 ID만 사용한다. 공 발사 수학·물리·HOME·PD·지연 수치는 변경하지 않았다.
후속 단계용 빈 파일(`rewards.py`, `observations.py` 등)은 요청한 폴더 구조의 일부여서 유지한다.

## 10. 실행과 자동 검사

실행에 사용하는 Python 환경에 MJLab과 MuJoCo가 설치되어 있어야 한다.
`BHuman_mujoco_getup/.venv/bin/python`은 BHuman 프로젝트의 별도 환경이므로
그곳에 MJLab이 없으면 `ModuleNotFoundError: No module named 'mjlab'`가 발생한다.
`main.py`가 소스 경로를 추가하는 기능은 외부 패키지를 자동 설치하는 기능이 아니다.

`Robocup-RL` 폴더에서는 다음 명령으로 이 프로젝트 전용 환경을 설치하고 실행한다.
`uv sync`는 `pyproject.toml`의 의존성을 `Goalkeeper_mjlab/.venv`에 설치한다.
다른 프로젝트의 가상환경을 수정하거나 참조할 필요가 없다.

```bash
uv sync --project Goalkeeper_mjlab --python 3.13
Goalkeeper_mjlab/.venv/bin/python Goalkeeper_mjlab/main.py --mode shots
```

`Goalkeeper_mjlab` 폴더 안에서 작업한다면 다음처럼 실행할 수도 있다.

```bash
uv sync --python 3.13
uv run python main.py --mode shots
```

아래 명령들은 `Goalkeeper_mjlab` 폴더에서 해당 가상환경을 활성화한 뒤 사용한다.
활성화하지 않는 경우 `python` 대신 `.venv/bin/python`을 쓰면 된다.
서버에서도 이 저장소의 `pyproject.toml`과 `uv.lock`으로 설치하며 노트북의 절대 경로는 필요하지 않다.

```bash
python main.py --mode shots
python main.py --mode shots --headless
python main.py --mode shots --headless --shots 20 --num-envs 4 --seed 0
python main.py --mode shots --ground-prob 1 --shot-speed 3 6 --shot-y -0.5 0.5
python main.py --mode shots --ground-prob 0 --air-launch-height 0.2 0.6
python -m unittest discover -s tests -p 'test_shots.py' -v
```

`shots` 모드의 MuJoCo 창에서 `P`는 물리 진행·정지, `R`은 새 랜덤 슛으로 초기화하는 동작이다.
마우스 드래그·스크롤로 시점을 이동하거나 확대·축소한다.
`H`는 기존 검사와 같이 Head Yaw 목표각을 바꾸는 기능이며, 발사 방향을 바꾸는 키는 아니다.

별도 `--mode`를 지정하지 않으면 기존과 동일하게 `motors` 모드를 실행한다.
슛 기능을 보려면 `--mode shots`를 지정한다.
viewer는 슛이 끝나면 다음 슛을 계속 발사하고, headless는 기본 10개 이상 에피소드가 끝나면 결과를 출력한다.
`--shots 20`은 **전체 병렬 환경에서 최소 20개 슛이 완료되면 끝내기**다.
같은 스텝에 여러 환경이 끝나면 최대 `병렬 환경 수 - 1`개 더 완료될 수 있으며 실제 완료 개수를 출력한다.

| 옵션 | 의미 |
| --- | --- |
| `--shots N` | 전체 환경에서 완료할 최소 에피소드 수 |
| `--num-envs N` | 병렬 환경 개수 |
| `--seed N` | 난수 재현용 seed |
| `--device cpu` | 실행 장치. 서버에서는 지원되는 CUDA 장치를 지정 가능 |
| `--ground-prob P` | 땅볼 확률 |
| `--shot-speed MIN MAX` | 발사 속도 범위, m/s |
| `--shot-distance MIN MAX` | 로봇 앞 출발 거리 범위, m |
| `--shot-y MIN MAX` | 출발 좌우 위치 범위, m |
| `--air-launch-height MIN MAX` | 뜬볼 출발 중심 높이, m |
| `--target-y-fraction MIN MAX` | 골문 유효 반폭에 대한 목표 좌우 비율 |
| `--air-target-height-fraction MIN MAX` | 골문 유효 높이에 대한 목표 높이 비율 |
| `--episode-seconds S` | 에피소드 제한 시간, s |
| `--goal-distance M` | 로봇 기준점~뒤쪽 골라인 거리, m. 현재 CLI 기본값 `0.5` |

`--report path.json`으로 보고서를 파일로 보관할 수 있다.
보고서가 필요할 때 지정하며 기본 실행이 매번 로그 파일을 생성하지는 않는다.
`--ball-x/y/z`는 기존 정적 초기 배치용 옵션이고, 랜덤 슛의 출발 범위는 `--shot-distance`, `--shot-y`,
`--air-launch-height`로 지정한다. 슛 reset에서는 샘플링된 공의 상태가 사용된다.

반복 검사 보고서는 다음 항목을 제공한다.

| 항목 | 의미 |
| --- | --- |
| `finite`, `passed` | 현재 시뮬레이션 상태에 NaN·무한대가 없는지. 선방 성공률이 아님 |
| `num_envs` | 실행한 병렬 환경 수 |
| `physics_hz`, `policy_hz` | 실제 설정에서 계산한 물리·정책 실행 빈도 |
| `completed_episodes` | 이번 반복 실행에서 실제로 완료한 슛 수 |

상세 슛 목록과 그 목록을 위한 종류별·접촉별 보고서는 제거했다.
학습 환경의 기본 `shot_goal`, `shot_touched`, `shot_out`, `shot_timeout` 에피소드 통계는 유지한다.
보고서의 `passed`는 수치 상태의 유효성 확인이며, 기능별 정확성은 `test_shots.py`에서 별도로 검사한다.

## 11. 검증 범위와 남아 있는 한계

자동 검사에서는 랜덤 범위·재현성·땅볼 회전·뜬볼 궤적·환경별 초기화·골라인 경계·실제 접촉을 확인한다.
2026-11-02 Mac CPU의 고정 MJLab 환경에서 **시작 목표각 회귀 검사를 포함한 3단계 자동 검사 24개가 모두 통과**했다.
`ruff` 검사도 통과했다. CUDA와 실제 하드웨어에서는 이번 단계의 실행 검사를 수행하지 않았다.

| 검사 묶음 | 확인한 내용 |
| --- | --- |
| 랜덤 슛 | 위치·속도·골문 목표 범위, 땅볼 비율 선택, 동일 seed 재현, 잘못된 값·도달 불가능한 조건 거부 |
| 속도 계산 | 뜬볼의 중력 궤적이 목표점에 도달하는지, 땅볼이 바닥에서 미끄럼 없이 굴러가도록 회전하는지 |
| 기본 초기화 | 선택한 환경만 reset, 자동 timeout·영역 이탈 후 새 발사, 원점 XYZ 이동 |
| 커리큘럼 연결 | 실행 중 설정 변경이 다음 reset 환경에만 적용되고 다른 환경의 슛·제한 시간·영역은 유지되는지 |
| 골라인 | 공 전체 통과·진행 방향·공 크기 경계·고속 통과 보간·득점 중복 방지·옆쪽에서의 잘못된 진입 거부 |
| 실제 접촉 | 기본 최고 8 m/s에서 골대 기둥 반사와 로봇 접촉·분리 후 기록 유지, 접촉 후 득점 동시 기록 |
| 실제 땅볼 | 3 m/s로 굴린 공의 골문 도달과 바닥 접촉 허용 오차 회귀 검사 |
| 검사 진입점 | 실제 subprocess로 `main.py --mode shots --headless --shots 3 --num-envs 2 --seed 7 --episode-seconds 0.12` 실행·JSON 결과 확인 |
| 검사 설정 | 반복 검사에 맞지 않는 `auto_reset=False`를 모델 컴파일 전에 거부 |
| 시작 명령 | 최초 생성과 이후 12개 물리 스텝의 실제 엔진 목표각이 HOME인지, 수동·자동·부분 reset에서도 유지되는지 확인 |

2026-11-02 불필요한 기록 정리 후에도 기존 `test_shots.py` **24개가 모두 통과**했다.
삭제한 보고서 필드 대신 실제 속도·엔진 상태·기본 종료 반환값으로 검사하도록 기존 테스트를 수정했다.

ZIP은 MuJoCo 모델과 자산을 보관하는 내보내기다.
랜덤 발사 이벤트·접촉 기록·골라인 판정의 Python 실행 코드까지 XML 안에 저장하는 기능은 아니다.
슛 파이프라인을 반복 실행할 때는 `Goalkeeper_mjlab` 패키지와 `--mode shots`를 사용한다.

전용 환경의 의존성 버전은 `uv.lock`에 기록했다. 가상환경 자체는 `.gitignore`로 제외한다.
lock 파일에 노트북의 절대 소스 경로나 인증정보를 넣지 않았으며, 다른 서버에서는 같은 저장소에서
`uv sync --locked --python 3.13`으로 해당 운영체제에 맞는 의존성을 설치한다.

공통 환경 정리와 시작 목표각 수정을 반영해 전체 57개를 다시 실행했다.
공·모터 수치를 바꾸지 않고 구성 책임과 호출 위치를 정리했으며 기존 동작 검사 기준을 유지했다.

기존 HOME 관련 실패는 다음 두 검사다. 기준을 낮추거나 실패를 건너뛰도록 수정하지 않았다.

- `test_motors.test_full_completion_criteria_use_shared_mjlab_code`: 자유 로봇의 자세 유지·목표각 추종 완료 기준.
- `test_portability`의 단독 폴더 모터 검사: `--check-motors --hold-seconds 1`에서 같은 HOME 자세 유지 문제로 실패.

기본 최고 속도 8 m/s에서 실제 골대 기둥 충돌과 짧은 로봇 접촉도 검사 항목에 포함한다.
3 m/s 땅볼의 실제 골문 도달 검사는 로봇을 멀리 옮겨 경로를 비운 조건에서 수행한다.
이는 공 발사·바닥 접촉·득점 판정 자체를 확인하기 위한 조건이며 실제 학습 로봇의 배치를 바꾸지 않는다.

이 작업 세션에서 `--render`를 통한 화면 검사는 `invalid CoreGraphics connection` 오류로 완료하지 못했다.
그래서 MuJoCo 창의 실제 표시·키 입력을 직접 눈으로 확인했다고 보고하지 않는다.
기존 native viewer에 슛 실행기를 연결했고 headless 상태·실제 엔진 접촉·명령행 실행은 검사했다.
GUI를 사용할 수 있는 로컬 Mac에서 `python main.py --mode shots`로 창을 확인할 수 있다.

현재 HOME 자세는 기존 고정 PD 목표각만으로 장시간 균형을 유지하는 검사에서 넘어지는 문제가 확인되어 있다.
HOME 자세 유지 문제는 이번 단계의 공 발사 구현과 분리해서 추적한다.
공 발사·접촉 기록 검증과 로봇의 균형·선방 정책 검증을 구분해야 한다.
로봇을 고정하거나 충돌을 분리한 검사는 궤적·판정을 살펴보는 검증 조건이며 실제 학습의 로봇을 고정한다는 뜻이 아니다.

공·골대의 접촉 물성은 wirlwind 팀 코드의 기존 값을 유지한다.
높은 속도에서는 접촉이 부드럽게 계산되면서 실제 물체가 일부 겹치는 현상이 커질 수 있다.
골라인 검사가 빠른 공의 이동을 잡는 것과, 엔진이 고속 충돌을 실제 공처럼 정확하게 재현하는 것은 서로 다른 검증 항목이다.
이번 검사 결과를 실제 하드웨어에서 공의 반발·마찰까지 검증한 결과로 해석하면 안 된다.
