## 2. 기본 실행과 화면 조작

`Goalkeeper_mjlab` 폴더 안에서 실행한다. Python 환경을 먼저 활성화한다. 다른 프로젝트 폴더는 필요 없다.

```bash
python main.py
```

`MuJoCo : goalkeeper_stage2` 창이 열리고, PD 제어를 켠 상태로 준비 자세를 유지한다.
macOS에서는 현재 Python에 맞는 mjpython으로 자동 전환한다.

- `P`: 물리 진행/정지.
- `R`: 준비 자세, 목표각, 시간, 지연 버퍼를 reset한다.
- `H`: 머리 Yaw 목표각을 +0.2 → -0.2 → 0 rad로 바꾼다. 0.2 rad는 약 11.46°다.
- 마우스 드래그/스크롤: 시점 변경/확대·축소.

처음부터 목표각을 주려면 다음과 같이 실행한다. `--joint`는 초기 자세 변경이고, `--target`은 모터가 따라갈 명령이다.

```bash
python main.py \
  --target Head_Yaw=0.2
```

화면 없는 완료 기준 검사는 다음 명령이다. 기본 10초의 시뮬레이션을 검사하며 실제 벽시계로 10초를 기다리는 방식은 아니다.

```bash
python main.py \
  --headless --check-motors --report /tmp/goalkeeper-stage2.json
```

단순히 `--headless`만 쓰면 설정/모델 연결 검사를 한다. 자세 유지·추종·220개 토크 사례까지 실행하려면 `--check-motors`를 붙인다.
성공은 JSON의 `passed: true`, 실패는 `errors` 항목과 종료 코드로 확인한다.

1단계의 모터 없는 모델은 다음 명령으로 재현한다.

```bash
python main.py --stage 1
```

1단계는 처음에 정지하고 `nu=0`, 2단계는 제어를 진행하며 `nu=22`다. 골대 실행 기본값 mid는 기존 설정을 사용한다.
공·골대 크기 옵션, 원점 이동, PNG·ZIP 내보내기 기능도 사용할 수 있다.

## 4. 물리 배경지식 없이 모터 설정 읽기

### 모터와 제어기는 서로 다른 설정이다

모터는 움직일 수 있는 한계를, 제어기는 그 안에서 어떻게 움직일지를 정한다.

| 항목 | 쉽게 설명하면 | 단위 |
| --- | --- | --- |
| `armature` | 모터 내부 회전 부품 때문에 관절 속도를 바꾸기 어려운 정도. 마찰처럼 에너지를 없애는 값과 구분한다 | kg·m² |
| `peak_effort` | 천천히 돌 때 모터가 낼 수 있다고 모델링한 최대 회전력(토크) | N·m |
| `velocity_limit` | 이 단순 모델에서 회전력을 낼 수 있는 속도의 끝 | rad/s |
| `knee_point_velocity` | 속도가 빨라지며 힘이 줄어들기 시작하는 지점. 여기의 knee는 무릎이 아니라 그래프의 꺾이는 지점이다 | rad/s |
| `kp` | 목표각과 차이가 날 때 얼마나 세게 되돌릴지 | N·m/rad |
| `kd` | 빠르게 움직이는 관절에 얼마나 제동을 걸지 | N·m·s/rad |
| `output_limit` | 프로그램이 요청하도록 허용한 회전력의 상한 | N·m |

예를 들어 kp=80이고 목표에서 0.1 rad 벗어났으며 속도가 0이면 8 Nm를 요청한다.
움직이는 중에는 kd가 계산한 제동 성분을 함께 반영한다.

```text
PD 요청 토크 = kp × (늦게 도착한 목표각 - 현재 각도) - kd × 현재 속도
실제 허용 토크 = min(프로그램 상한, 현재 속도에서의 모터 한계)
```

`kd`는 프로그램이 내는 제동 힘의 설정이다. XML joint의 수동 `damping`이나 `frictionloss`와 별개다.
`armature`도 PD gain과 다른 값이므로 모터 설정 파일에 분리했다.

### 모터가 빨라지면 힘이 줄어드는 모델

```text
느린 구간                  힘이 줄어드는 구간               최고 속도 이상
|속도| <= 감소 시작         감소 시작 < |속도| < 최고속도     |속도| >= 최고속도
최대 토크 유지             직선으로 0까지 감소              모터 토크 0
```

회전 방향이 반대여도 속도 크기가 같으면 같은 한계를 사용한다.
공식 코드와 같은 단순화로 최고 속도 이상에서는 제동 토크까지 0으로 본다.
실제 관절 속도를 강제로 잘라내는 구현은 아니다. 외력/접촉으로 그 속도를 넘을 수 있다.

```text
비율 = clip((최고속도 - |현재속도|) / (최고속도 - 유효 감소 시작 속도), 0, 1)
물리 한계 = 모터 최대 토크 × 비율
최종 한계 = min(제어기 출력 상한, 물리 한계)
```

공식과 동일하게 분모의 최소값은 1e-6으로 두어 0 나눗셈을 막는다.
Booster 공식 Head 값은 감소 시작 10.47이 최고 속도 7.85보다 크므로, Booster 공식 숫자는 보존하고 계산 시 유효 시작 속도를 7.85로 제한한다.

프로그램 상한을 먼저 줄인 뒤 속도 비율을 곱하면 잘못된 결과가 된다.
예를 들어 물리 한계가 21.5 Nm, 프로그램 상한이 5 Nm면 최종 한계는 5 Nm다. 5에 0.5를 곱한 2.5 Nm가 아니다.

두 모터가 있으니 토크도 무조건 2배라고 가정하지 않았다. 현재 serial 발목의 환산값으로 적용하며 자세별 연결 기구를 상세하게 계산하는 모델은 아니다.

```bash

  --headless --motor-source legacy
```

이 옵션은 모터 물리 테이블만 바꾼다. PD·제어기 상한·지연까지 과거 학습 전체를 재현하는 옵션은 아니다.
예를 들어 legacy Hip Roll 물리 최대값이 76이어도 기본 제어기 상한은 43이므로 실제 출력은 여전히 그 상한을 넘지 않는다.

## 6. PD 설정과 공식과의 차이

**기본 gain은 공식 최신값과 다르다.** 현재 MJCF에서 정책 없이 준비 자세를 유지하는 검증용 설정으로,
wirlwind 팀 코드의 `k1_constants.py`에 있는 gain을 사용했다. 제어기 출력 상한은 별도 필드로 명시했다.

| 그룹 | 기본 kp / kd | 공식 K1 계산값 kp / kd (참고) | 프로그램 출력 상한 Nm |
| --- | --- | --- | ---: |
| head | 4 / 0.25 | 3.947842 / 0.251327 | 6 |
| arm | 10 / 1 | 3.947842 / 0.251327 | 14 |
| hip_pitch | 80 / 4 | 30.200989 / 3.604978 | 68 |
| hip_roll | 80 / 4 | 21.447961 / 2.560162 | 43 |
| hip_yaw | 80 / 4 | 17.846013 / 2.130211 | 38.3 |
| knee | 80 / 4 | 60.401979 / 4.806637 | 112 |
| ankle_pitch | 50 / 2 | 24.984419 / 2.982295 | 38.3 |
| ankle_roll | 50 / 2 | 7.138405 / 0.852084 | 38.3 |

공식은 `Kp = armature × (2πf)²`, `Kd = 2 × 감쇠비 × armature × 2πf`로 gain을 계산한다.
K1 다리는 f=4, arm/head는 상속 기본 f=10을 사용한다. 이 f는 gain 계산용 반응 특성이며 정책 호출 주기 50 Hz와 구분한다.
비교 함수 `official_reference_controllers()`에 공식 계산식을 별도로 남겼다.

공식 계산값을 현재 MJCF의 준비 자세에 적용한 별도 10초 실험에서는 몸통 최저 높이 약 0.0546 m,
최대 기울기 약 93.37°로 자세 유지에 실패했다. 이는 공식 학습 설정 자체가 틀렸다는 결론이 아니다.
공식은 정책과 함께 사용하는 설정이며, 여기의 완료 기준은 학습 정책 없이 일정 목표각만으로 서 있기다.
이 조건에 맞는 별도 hold gain을 기본으로 선택하고 출처 차이를 표시했다.

준비 자세의 관절각은 공식 K1 init_state를 따른다. 어깨 Roll만 -1.3/+1.3 rad, 나머지는 0 rad다.
몸통 높이는 공식의 0.57을 그대로 복사하지 않고 현재 모델의 발바닥에서 계산한다. 초기값은 약 0.552924 m다.
1단계에서 다리를 굽힌 HOME는 모델 검사용으로 유지하며, 2단계의 검증용 준비 자세와 구분한다.
이 준비 자세를 최종 골키퍼 방어 자세로 확정한 것은 아니다.

공식 gain 결과를 직접 비교하려면 다음 코드를 현재 MuJoCo 환경에서 실행할 수 있다.

```python
from goalkeeper_mjlab.motor_runtime import MotorSimulation
from goalkeeper_mjlab.robots.k1.controller_profiles import official_reference_controllers
from goalkeeper_mjlab.robots.k1.motor_parameters import get_motors
from goalkeeper_mjlab.tasks.goalkeeper.config.k1.motor_scene_cfg import Stage2SceneCfg

cfg = Stage2SceneCfg(controllers=official_reference_controllers(get_motors()))
print(MotorSimulation(cfg).run(10.0))
```

## 7. 물리 시간과 정책 시간

| 설정 | 기본값 | 출처/의도 |
| --- | --- | --- |
| 물리 간격 `physics_dt` | 0.005 s | Booster 공식 코드와 wirlwind 팀 코드의 50 Hz 구성에 사용되는 물리 간격 |
| `decimation` | 4 | 목표각 한 번을 잡고 물리를 네 번 계산 |
| 정책/명령 주기 | 0.020 s = 50 Hz | `physics_dt × decimation` |
| 적분기 | implicitfast | MuJoCo 내장 PD의 제동 효과를 적분에 반영하는 프레임워크 이식 |
| 접촉 솔버 | Newton | MuJoCo 설정. 공식 Isaac/PhysX와 엔진이 다름 |
| 솔버 반복 수 | 10 | wirlwind 팀 코드 |
| line search 반복 수 | 20 | wirlwind 팀 코드 |
| 수렴 오차 | 1e-8 | wirlwind K1 XML/프레임워크 기본 |
| 마찰 계산 | elliptic | 1단계 공의 구름 저항 변환 전제 유지 |
| 중력/기둥·공·바닥 접촉 | 1단계 구성 | wirlwind 참조 자산의 물리 구성 재사용 |

적분기는 현재 위치·속도·힘으로 다음 순간을 계산하는 방법이다.
접촉 솔버는 도형이 서로 누르는 상황에서 일관된 힘을 찾는 반복 계산이다.
정책 목표각은 20 ms 동안 유지하지만, **PD 피드백과 속도별 토크 상한은 매 5 ms 물리 스텝에 갱신**한다.

시간 설정을 바꾸는 예:

```bash
python main.py \
  --physics-dt 0.002 --decimation 10 --delay-min 5 --delay-max 20
```

이 예는 정책 주기 20 ms와 지연 10~40 ms를 유지하면서 물리 계산만 2 ms로 바꾼다.
delay 숫자는 물리 스텝 수이므로 dt를 바꾸면 밀리초 값도 함께 검토해야 한다.

## 8. 명령 지연과 reset

- 기본은 공식 K1처럼 그룹/환경별 2~8 물리 스텝(10~40 ms)을 reset 시 한 번 선택한다.
- 다리, 발목, 팔, 머리 그룹을 분리하며 같은 그룹의 관절은 같은 지연을 쓴다.
- 다음 reset까지 선택한 지연을 유지한다. wirlwind 팀 코드의 매 스텝 재샘플링/hold probability 0.3과 구분한다.
- 늦어지는 것은 목표각 명령이다. 현재 관절각/속도 피드백은 최신 값을 사용한다.
- reset 시 명령 이력은 준비 자세로 채운다. 과거 명령이나 임의의 0 rad가 다음 에피소드로 넘어가지 않게 하는 프로젝트 초기화 정책이다.
- 일부 환경만 reset하면 다른 환경의 명령 이력·지연을 유지한다.

지연 없이 제어만 확인하려면 `--delay-min 0 --delay-max 0`으로 실행한다.
기본 seed=0은 검사 재현용이다. 학습 환경의 seed를 결정할 때 `Stage2SceneCfg.seed`에도 연결해야 한다.
NumPy와 Torch는 RNG가 달라 같은 seed라도 두 백엔드에서 같은 지연 배열을 뽑는다고 가정하지 않는다.

## 9. 실제 힘에 제한을 적용하는 경로

```text
정책/사용자 목표각(rad)
  → 명령 지연 버퍼
  → 현재 속도로 물리 토크 한계 계산
  → 프로그램 출력 상한과 min
  → 엔진 actuator_forcerange에 [-상한, +상한] 기록
  → 엔진 ctrl에 지연된 목표각 기록
  → MuJoCo 내장 PD와 물리 스텝
  → 실제 qfrc_actuator / actuator_force 검사
```

**ctrl은 목표각(rad), forcerange는 토크(Nm)**다. 두 숫자의 단위를 혼합하지 않았다.
현재 모델은 관절마다 actuator 하나, gear=1이므로 actuator force를 관절 토크와 직접 대응시킬 수 있다.
각 관절의 armature는 실제 joint 필드에 덮어써 동역학에 반영한다. wirlwind 참조 XML 파일은 보존한다.

공식은 Isaac의 명시적 PD+클립, 우리는 wirlwind 팀의 MJLab 이식처럼 MuJoCo 내장 위치 PD+실제 forcerange를 사용한다.
파이썬에서 토크 숫자만 계산하는 방식과 달리, implicitfast가 제어기의 제동 효과를 적분에 포함할 수 있다.
네이티브에서 명시적 PD만 사용한 비교 실행에서는 관절 진동이 커져 이 방식을 선택했다.

MJLab에서는 한 모델을 여러 환경이 공유한다. 환경별 속도가 다른데 힘 상한을 하나만 쓰면 잘못된 결과가 나온다.
`bind_motor_limits()`가 `actuator_forcerange`를 환경별 배열로 확장하고 각 actuator에 tensor bridge를 연결한다.
CUDA graph는 확장한 배열의 주소를 사용하도록 MJLab의 공식 확장 API를 통해 다시 구성한다.
상한 배열을 미리 캐시하지 않고 매번 bridge에서 읽어, 배열 확장 후 이전 메모리를 계속 쓰는 문제를 피했다.
연결을 빠뜨리면 제한 없이 진행하지 않고 RuntimeError를 내도록 했다.

### 정책 없이 MJLab 장면만 실행할 때

```python
from dataclasses import replace
from goalkeeper_mjlab.motor_runtime import BatchedMotorSimulation
from goalkeeper_mjlab.tasks.goalkeeper.config.k1.motor_scene_cfg import Stage2SceneCfg

cfg = Stage2SceneCfg()
cfg = replace(cfg, scene=replace(cfg.scene, num_envs=2))
runtime = BatchedMotorSimulation(cfg, device="cpu")
target = runtime.robot.data.default_joint_pos.clone()
target[:, runtime.robot.joint_names.index("Head_Yaw")] = 0.2
for _ in range(100):
    runtime.step(target)  # 한 번당 20 ms, 내부에서 물리 4번
```

준비된 CUDA 환경에서는 device를 해당 장치로 지정할 수 있지만, 본 문서의 실행 확인은 CPU 기준이다.
직접 Scene/Simulation을 조립한다면 `scene.initialize(sim.mj_model, sim.model, sim.data)`와
`bind_motor_limits(scene, sim)`을 사용한다. raw `wp_model/wp_data` 대신 tensor bridge를 전달해야 한다.

## 14. 내보내기와 다음 단계

PNG/ZIP/JSON 옵션은 기존과 같다. ZIP에는 22개 내장 PD actuator, 고정 출력 상한, 초기 목표각, XML·메시가 들어간다.
**속도별 상한 갱신과 명령 지연은 Python 실행 코드의 기능**이므로 ZIP만 다른 MuJoCo에 열면 이 동작까지 자동 복제되지는 않는다.
동일한 모터 동작을 재현하려면 이 패키지의 실행기 또는 MJLab actuator를 함께 사용해야 한다.

다음 3단계는 현재 준비 자세 reset 경로를 바탕으로 공의 초기 위치/발사 속도, 슈팅 샘플러, 에피소드 reset을 연결하는 작업이다.
정책 관측/action 계약, 보상/종료, PPO 등록은 이후 단계에 연결한다.

## 15. 서버에는 Goalkeeper_mjlab만 배포한다

이 저장소는 부모 폴더 이름/위치, wirlwind 팀 코드 저장소(`booster_mjlab`), `inha_mjlab`, Mac의 기존 가상환경을 필요로 하지 않는다.
XML·STL·OBJ·두 JSON·실행 모듈을 모두 이 저장소 안에 포함한다. 아래 명령의 작업 폴더는 clone한 `Goalkeeper_mjlab` 자체다.
Python 3.13 환경을 활성화한 다음 진행한다. 현재 고정 MJLab은 Python 3.14 미만을 요구한다.

```bash
cd Goalkeeper_mjlab
# 기존 서버 환경에 MuJoCo/MJLab이 준비됐다면 기본 패키지만 등록한다.
python -m pip install -e .
python main.py --headless --check-motors
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python -m unittest discover -s tests -v
```

MJLab 설치까지 필요한 새 환경에서만 `python -m pip install -e '.[training]'`을 사용한다.
training extra는 표준 Git URL로 검증한 커밋을 지정해 pip와 uv가 같은 코드를 받는다.
이 설치에는 GitHub 접속이 필요하지만, 설치 후 모델 실행·JSON 검증은 GitHub에 접속하지 않는다.
CUDA용 Torch 설치 방식은 서버의 기존 환경에 따른다. 위 명령은 아직 PPO 학습 명령이 아니라 2단계 구성/동작 검사다.
화면 없는 서버에서는 `--headless`로 실행한다. 기본 GUI는 Mac/화면이 있는 컴퓨터에서 사용한다.

### JSON의 경로를 읽는 방법

| 항목 | 의미 | 실행 시 사용 여부 |
| --- | --- | --- |
| asset_manifest.json의 files 키 | 예: robots/k1/xmls/k1.xml. 설치된 goalkeeper_mjlab 패키지 디렉터리 기준 상대경로 | 이 파일의 바이트를 읽어 SHA-256 비교 |
| 같은 레코드의 source_path | wirlwind GitHub 저장소 안에서 복사해 온 파일의 위치 | 출처 기록만 하며 경로를 열지 않음 |
| motor_reference.json의 official_motors/local_reference_motors | 함께 배포한 수치 기준표 | 패키지 내부 JSON의 숫자를 비교 |
| official_files의 URL·SHA, local_reference_repository/commit | 어디에서 어떤 버전을 확인했는지 남기는 출처 | 원격 URL 또는 다른 저장소를 열지 않음 |

PACKAGE_ROOT는 `__file__`에서 구하므로 현재 작업 폴더와 무관하다.
local_reference라는 이름은 비교했던 wirlwind 팀 코드를 뜻한다. 노트북의 로컬 폴더 경로라는 뜻이 아니다.
JSON의 설명과 로더 주석에도 이 구분을 적었다. 검증 결과, 이 두 JSON에 실행용 외부 경로 의존성은 없었다.

### 독립성 검사를 재현하는 방법

```bash
PYTHONPATH=src python -m unittest discover -s tests -p test_portability.py -v
```

이 검사는 저장소를 임시 경로로 복사하고, 출처 source_path와 URL을 무효화하며,
복사 전 저장소 읽기와 네트워크 연결을 audit hook으로 거부한다. PYTHONPATH도 제거한 별도 작업 폴더에서
복사본의 main.py로 1단계와 2단계 동역학 검사를 실행한다.
별도로 독립 복사본에서 전체 MJLab/Warp CPU 검사도 실행해 배치 actuator의 동작을 확인했다.
Linux/CUDA 서버 자체에서 실행한 결과는 아니므로 실제 서버의 드라이버·CUDA 호환성까지 확인한 것으로 해석하면 안 된다.
