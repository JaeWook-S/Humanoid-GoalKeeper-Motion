# 구현 2단계: K1 모터·제어와 wirlwind 구조 정리

최근 수정: 2026-11-01. 구현 단계 번호는 설명 문서에서만 사용한다.
학습 코드의 `Stage1SceneCfg`·`Stage2SceneCfg`와 단계별 장면 연결은 제거했다.

## 1. 현재 구조와 읽는 순서

wirlwind의 `k1_constants.py → get_k1_robot_cfg() → env_cfgs.py` 구성을 따른다.
기존 프로젝트의 `robots/k1/constants.py` 경로는 유지했다. 실제 설정값은 한곳에서 읽을 수 있게 모았다.

```text
src/goalkeeper_mjlab/
├── robots/k1/
│   ├── constants.py           # 수치·자세·충돌·지연·로봇 설정 생성
│   ├── actuators.py           # 모터/PD 자료형, 기본 actuator 설정 클래스
│   ├── torque_speed.py        # 환경별 속도-토크 상한 갱신
│   ├── motor_reference.json   # 공식/wirlwind 비교 기준·출처
│   └── xmls/                  # 보존한 모델과 메시
├── tasks/goalkeeper/config/k1/
│   ├── env_cfgs.py            # 장면·물리·decimation·startup/reset 이벤트
│   ├── rl_cfg.py              # 후속 PPO 설정, 현재 빈 틀
│   └── policy_contract.py     # 후속 관측/action 계약, 현재 빈 틀
├── validation/                # 학습에서는 import하지 않는 검사 도구
│   ├── geometry.py            # 모터를 뺀 형상/접촉 검사
│   ├── motor_runtime.py       # 같은 모터 구현의 화면·검사 실행기
│   └── motor_checks.py        # 자세·목표각·실제 토크 검사
└── scripts/inspect_scene.py    # MuJoCo 화면·검사 CLI

tests/
├── test_geometry.py
├── test_motors.py
└── test_portability.py
```

코드 분석은 **constants.py → actuators.py → torque_speed.py → env_cfgs.py** 순서가 적합하다.
`constants.py`에서 모르는 자료형이 나오면 `actuators.py`의 해당 클래스만 확인하면 된다.
화면·테스트의 실행 흐름을 볼 때만 `validation/`과 `scripts/`를 추가로 읽는다.

| 구분 | 파일/함수 | 책임 |
| --- | --- | --- |
| 실제 학습 공통 | `constants.py` | 모델 경로·22관절 순서·HOME 준비 자세·FULL_COLLISION·모터/PD 표·ACTUATOR_DELAY |
| 실제 학습 공통 | `get_k1_robot_cfg()` | 새 K1 Entity 설정을 생성. 관절별 물성·기본 actuator·충돌·초기 자세 연결 |
| 실제 학습 공통 | `actuators.py` | 수치를 담는 MotorParameters/ControllerParameters와 MotorPositionActuatorCfg 정의 |
| 실제 학습 공통 | `torque_speed.py` | 실제 현재 관절 속도로 환경별 토크 상한을 갱신하는 MotorEntity |
| 실제 학습 공통 | `make_goalkeeper_env_cfg()` | **MJLab 기본 ManagerBasedRlEnvCfg** 반환. 별도 Stage/실행 설정 wrapper 없음 |
| 검증 전용 | `validation/geometry.py` | 학습 장면을 복사해 모터를 빼고 형상·배치·접촉 검사 |
| 검증 전용 | `validation/motor_runtime.py` | 학습 설정의 Scene/Simulation을 실행하고 viewer로 결과 복사 |
| 검증 전용 | `validation/motor_checks.py` | 공통 엔진 출력에 완료 기준 검사. 별도 모터 모델 없음 |
| 화면·검사 진입점 | `main.py`, `scripts/inspect_scene.py` | GUI·키 처리·CLI·JSON/PNG/ZIP |
| 자동 검증 | `tests/` | 자산, 실제 엔진, 실제 RL 환경 연결, 단독 폴더 실행 검사 |

물리 한계와 PD는 서로 다른 자료형으로 유지한다. 파일을 나눠야만 둘을 구분할 수 있는 것은 아니다.
PD 필드명은 wirlwind·MJLab과 같은 `stiffness`, `damping`으로 통일했다.
설정 생성·검증 계산·JSON 보고서의 controllers 항목도 같은 이름을 사용한다. 제어 수치는 그대로다.
학습 설정이 `validation/`이나 `scripts/`를 import하지 않는 것도 새 프로세스에서 검사한다.

## 2. 설치와 실행

Python 3.13.x에서 Goalkeeper_mjlab만 clone하면 된다. 고정 MJLab의 Python 지원 범위에 맞춰 `<3.14`를 명시했다.

```bash
python -m pip install -e .
python main.py
```

MJLab/Torch/Warp는 필수 의존성이다. Mac CPU에서도 화면·검사를 실행할 수 있다.
다른 프로젝트 폴더나 해당 노트북의 절대 경로는 필요하지 않다.

- `P`: 물리 진행/정지.
- `R`: 초기 상태와 목표각 복원. 모터 모드는 MJLab 기본 reset 사용.
- `H`: 모터 모드에서 Head Yaw 목표각 0 → +0.2 → -0.2 → 0 rad.
- 마우스 드래그/스크롤: 시점 변경/확대·축소.

```bash
python main.py --headless
python main.py --headless --check-motors
python main.py --target Head_Yaw=0.2
python main.py --mode geometry
python main.py --mode geometry --headless --mjlab-check
```

`--mode motors`가 기본이다. `--mode geometry`는 모터 없는 정적 형상 검사다.
옛 `--stage 1/2` 옵션은 제거했다. 구현 순서를 실행 모드 이름으로 사용하지 않는다.
macOS에서는 같은 Python 환경의 mjpython으로 자동 전환하며 기본 실행은 MuJoCo 창을 연다.

## 3. 로봇 설정과 환경 설정

`constants.py`의 `get_k1_robot_cfg()`는 wirlwind처럼 로봇 설정을 생성한다.
모터 물리 표, PD 표, 준비 자세, 충돌 설정, 기본 명령 지연을 이 파일에서 관리한다.
`make_k1_articulation()`이 새 actuator 설정을 만들며 `K1_ARTICULATION`도 기본 구성으로 제공한다.
모터마다 물리값이 달라 종류별 actuator는 필요하다. 이것은 사용자 정의 지연 그룹이 아니다.

`env_cfgs.py`는 이 로봇과 공·골대·바닥을 배치하고 `SimulationCfg`, `MujocoCfg`, `decimation`을 직접 설정한다.
이전의 PhysicsControlCfg 변환 계층과 Stage1→Stage2 장면 연결은 없다.

```python
from goalkeeper_mjlab.tasks.goalkeeper.config.k1.env_cfgs import make_goalkeeper_env_cfg

cfg = make_goalkeeper_env_cfg(num_envs=4096)
# cfg는 MJLab 기본 ManagerBasedRlEnvCfg다.
# cfg.scene: 로봇·공·골대·바닥
# cfg.sim.mujoco: 물리 시간 간격·적분기·접촉 솔버
# cfg.decimation: 정책 한 번당 물리 스텝 수
# cfg.events: 기본 reset과 속도별 토크 제한 startup 연결
```

현재 관측/action/보상/종료/PPO 설정은 후속 구현 대상이다. 이 함수만으로 완성된 골키퍼 PPO 학습을 시작할 수는 없다.
검사 실행기는 정책 대신 준비 자세 또는 지정한 목표각을 입력한다.
실제 ManagerBasedRlEnv 생성·reset·물리 step도 검사했지만, 이 검사는 빈 action/관측을 사용하며 PPO 검사가 아니다.

## 4. 기본 명령 지연과 부분 reset

`constants.py`의 `ACTUATOR_DELAY` 기본값은 wirlwind와 같은 2~8스텝, hold 확률 0.3이다.

| 설정 | 의미 |
| --- | --- |
| `delay_min_lag=2`, `delay_max_lag=8` | 물리 스텝 기준 지연 범위. 현재 5 ms에서 10~40 ms |
| `delay_hold_prob=0.3` | 매 물리 스텝에서 이전 지연을 유지할 확률. 0.3초가 아님 |
| `cfg.seed` | 기본 Torch 난수의 재현에 사용. 실제 학습도 전체 학습 seed와 연결 |

70% 확률로 범위에서 다시 뽑는다. 재추첨한 값이 이전과 같을 수도 있다.
현재 모든 actuator가 같은 기본 타입/지연 설정을 사용하므로 MJLab이 한 환경의 관절들을 하나의 버퍼로 합친다.
환경마다 지연은 독립적이며, 직접 만든 지연 버퍼·그룹별 RNG·부분 reset 코드는 없다.

부분 reset은 MJLab의 Simulation/Scene reset과 기본 `reset_scene_to_default` 이벤트를 사용한다.
로봇·공·mocap 골대의 상태와 환경 원점 오프셋을 복원한다.
reset 후 과거 입력이 없으면 기본 버퍼는 첫 새 명령으로 이력을 채우므로 첫 명령이 바로 적용될 수 있다.
초기 lag도 0으로 시작할 수 있다. 준비 자세를 과거 이력에 강제로 채우는 코드를 추가하지 않았다.

```bash
python main.py --delay-min 0 --delay-max 0
python main.py --delay-min 2 --delay-max 8 --delay-hold-prob 0.3
```

## 5. 속도별 토크 제한

`torque_speed.py`의 Torch TorqueSpeedLimits와 MotorEntity를 학습·검증에서 공통 사용한다.
`MotorEntity.write_data_to_sim()`에서 기본 actuator가 명령을 처리한 뒤, 물리를 진행하기 전에 현재 속도로 힘 상한을 갱신한다.
이 연결 위치는 wirlwind tracking 환경과 같다. 현재 속도 피드백에는 명령 지연을 적용하지 않는다.

```text
감소 시작 속도 이하: 물리 최대 토크
감소 시작~최고 속도: 직선으로 감소
최고 속도 이상: 0
→ 프로그램 출력 상한과 min
→ 환경별 actuator_forcerange에 [-상한, +상한] 기록
→ 실제 물리 진행
```

**wirlwind와 구분:** 물리 최대 토크와 프로그램 상한을 분리했다.
물리 43 Nm가 속도 때문에 21.5 Nm로 줄고 프로그램 상한이 5 Nm이면 결과는 5 Nm다.
프로그램 상한 5에 속도 비율 0.5를 먼저 곱해 2.5 Nm로 만들지 않는다.
`ctrl`은 목표각(rad), `actuator_forcerange`는 허용 토크(N·m), `sim.data.actuator_force`는 실제 엔진 출력이다.
필수 startup 연결은 환경 생성 함수에서 등록하며, 초기화가 빠지면 오류를 내고 멈춘다.
actuators.py의 MotorPositionActuatorCfg는 wirlwind tracking과 동일하게 설정 생성 시
joint transmission인지, effort_limit이 None이 아닌지 검사한다. 검사 범위는 9절에 기록했다.

## 6. 물리값·제어값과 출처 차이

`booster_mjlab`은 **wirlwind 팀 코드**, 제조사 공식 코드는 **BoosterRobotics/booster_train**이다.

| 기준 | 고정 커밋 / 역할 |
| --- | --- |
| BoosterRobotics/booster_train | `83037fde138c49cd8d6459a4b592538e6e979ffb`: 기본 모터 물리값 |
| wirlwind 팀 코드 | `d92e11395d961096d639446c0a8a176f12bb51da`: PD·로봇 설정 구조·토크 제한 연결 참고 |
| MJLab | `b517e0c489139e7fcee95702cfb2b01931264985`: 기본 actuator/지연/reset/시뮬레이션 |

공식 참조: [actuator.py](https://github.com/BoosterRobotics/booster_train/blob/83037fde138c49cd8d6459a4b592538e6e979ffb/source/booster_train/booster_train/assets/robots/actuator.py), [booster_k1.py](https://github.com/BoosterRobotics/booster_train/blob/83037fde138c49cd8d6459a4b592538e6e979ffb/source/booster_train/booster_train/assets/robots/booster_k1.py).
URL·해시·수치 대조 기준은 motor_reference.json에 보관하며 런타임 네트워크/원본 저장소 접근은 없다.
수치는 공식 학습 코드의 모터 모델이며 실물 측정값으로 확정한 것은 아니다.

| 항목 | 쉽게 설명하면 | 단위 |
| --- | --- | --- |
| armature | 모터 내부 회전 부품 때문에 관절 속도를 바꾸기 어려운 정도. 마찰과 다름 | kg·m² |
| peak_effort | 천천히 회전할 때 낼 수 있는 최대 회전력 | N·m |
| velocity_limit | 모델에서 회전력이 0이 되는 최고 속도 | rad/s |
| knee_point_velocity | 토크가 감소하기 시작하는 속도. knee는 그래프의 꺾이는 점 | rad/s |
| stiffness | 목표각 오차를 되돌리는 힘의 크기 | N·m/rad |
| damping | 현재 속도에 비례해 제동을 거는 정도 | N·m·s/rad |
| output_limit | 프로그램에서 허용한 토크 상한 | N·m |

- PD 기본값(stiffness/damping): 머리 4/0.25, 팔 10/1, 엉덩이·무릎 80/4, 발목 50/2. wirlwind 테이블을 사용한다.
- Hip Roll 물리값: 공식 43 Nm / 최고 12.15 / 감소 시작 8.38 rad/s. wirlwind는 76 / 12.57 / 2.62다.
- 발목 armature: 공식 pitch ×1.4, roll ×0.4. wirlwind 비교값은 둘 다 ×2다.
- 공식 예시 어깨 Roll ±1.3 rad와 달리 현재 사용자 준비 자세 ±1.4 rad를 보존했다.
- 학습·모터 화면·형상 검사 모두 wirlwind HOME 관절각을 기본으로 사용한다. 초기 높이는 발바닥 메시에서 계산한다.
- `soft_joint_pos_limit_factor=0.9`로 wirlwind와 같다.
- `FULL_COLLISION.disable_other_geoms=False`를 보존했다. wirlwind 기본 True와 달리 선택하지 않은 XML 형상의 충돌 마스크를 유지한다.
- `--motor-source legacy`는 물리 표 비교용이며 wirlwind 학습 전체를 재현하는 옵션이 아니다.

HOME 변경에서는 기본 준비 자세만 바꾸었다. 모터 물리값·PD gain·발목 armature·기본 주기·토크 제한 계산식은 유지했다.
공·골대·로봇 자산 31개도 수정하지 않았다.

물리는 200 Hz(dt=0.005), 정책/목표각 슬롯은 50 Hz, decimation=4다.
implicitfast 적분기, Newton 접촉 솔버, iterations=10, ls_iterations=20, tolerance=1e-8을 쓴다.
iterations는 물리 스텝 안에서 접촉 해를 찾는 반복 수다. 공의 구름 저항에 맞춰 elliptic friction cone을 사용한다.

```bash
python main.py --physics-dt 0.002 --decimation 10 --delay-min 5 --delay-max 20
```

이 예는 정책 50 Hz와 지연 10~40 ms를 유지하며 물리를 500 Hz로 바꾼다. 기본값 변경은 아니다.

## 7. 검증 코드 분리와 삭제 내역

학습에서 검사용 scene이나 실행기를 호출하지 않는다. 검사가 학습 설정을 불러 쓴다.
검사 helper를 validation/ 패키지에 둔 이유는 설치된 CLI에서도 검사와 화면을 실행해야 하기 때문이다.
자동 테스트 파일만 tests/에 두고, 학습 코드의 import 경로에서는 validation/을 사용하지 않는다.

- `motor_parameters.py`, `pd_controller_cfg.py`: 값은 constants.py, 자료형은 actuators.py로 통합하고 기존 파일 삭제.
- `scene_cfg.py`, `robot_control_cfg.py`, `simulation_cfg.py`: 학습 구성은 env_cfgs.py로 통합하고 기존 파일 삭제.
- Stage1SceneCfg, Stage2SceneCfg, PhysicsControlCfg, make_mjlab_scene_cfg, make_controlled_mjlab_scene_cfg 제거.
- 루트의 inspection.py → validation/geometry.py, motor_runtime.py·motor_checks.py → validation/ 아래로 이동.
- test_stage1.py → test_geometry.py, test_stage2.py → test_motors.py로 목적에 따라 변경.
- 이전에 제거한 command_delay.py, mjlab_actuators.py, test_stage2_mjlab.py와 중복 NumPy 모터 모델도 복구하지 않음.

`make_geometry_env_cfg()`는 공통 HOME 자세와 형상 검사 간격 0.002초를 학습 생성 함수에 입력한다. 모터 모드의 기본 물리 간격은 계속 0.005초다.
`make_geometry_scene_cfg()`는 학습 SceneCfg를 복사하고 모터만 제거한다. 장면 조립은 MJLab 기본 Scene을 사용한다.
검사용 별도 장면 설정 클래스, 직접 만든 바닥/로봇/공/골대 attach 경로는 없다.
검사 원점 이동은 복사한 장면에만 적용하므로 학습 설정이나 다른 검사에 누적되지 않는다.

MotorSimulation은 같은 cfg.scene/cfg.sim과 실제 MotorEntity를 실행한다. PD·지연·토크를 재구현하지 않는다.
viewer에는 결과를 복사하고 mj_forward()로 그린다. 별도의 mj_step()으로 모터 물리를 다시 계산하지 않는다.
JSON의 토크 검증은 화면용 CPU MjData가 아니라 실제 MJLab sim.data 값을 사용한다.
ZIP은 기본 MJLab exporter로 저장하며 Python의 지연/속도별 토크 갱신 코드는 포함하지 않는다.

## 9. HOME 준비 자세 변경과 토크 제한 설정 검사

2026-11-01 추가 수정. 사용자가 요청한 wirlwind HOME 관절각을 학습·화면·검사의 기본 준비 자세로 적용했다.

| Elbow Yaw | -0.4 / +0.4 |

| Knee Pitch | +0.8 / +0.8 |

- constants.py의 HOME_POSE를 get_k1_robot_cfg(), make_goalkeeper_env_cfg(), CLI가 함께 사용한다.

**HOME의 고정 PD 자세 유지는 기존 완료 기준을 통과하지 못한다.**
이전 직립 자세의 통과 결과는 모터·지연·토크 적용의 근거이며, 다른 자세의 자유 기저 균형까지 보장하지 않는다.
기존 테스트의 통과 기준을 완화하거나 실패를 skip 처리하지 않았다.

hold["passed"]를 기본 bool로 변환해, 실패 결과도 JSON으로 출력·저장되게 고쳤다. 물리 계산이나 통과 기준은 바꾸지 않았다.

### 토크 제한 설정 검사 — wirlwind와 동일한 범위 반영

사용자 요청에 따라 wirlwind tracking의 BoosterPositionActuatorCfg와 같은 두 검사만 반영했다.
최종 상한 계산식과 수치는 유지한다.

```text
최종 상한 = min(현재 속도에서 낼 수 있는 물리 토크, 프로그램 출력 상한)
```

구현 위치는 robots/k1/actuators.py의 MotorPositionActuatorCfg.__post_init__()다.

1. super().__post_init__()으로 MJLab 기본 검사를 유지한다.
2. transmission_type이 JOINT가 아니면 ValueError를 낸다.
3. effort_limit이 None이면 ValueError를 낸다.

설정 객체를 생성할 때 검사하며 dataclasses.replace()로 새 설정을 만들 때도 실행된다.
build()에는 기존 MotorEntity 타입 확인을 유지했다. 매 물리 스텝의 토크 갱신은 기존 코드 그대로다.
앞서 제안한 effort_limit의 NaN/무한대/0 이하 검사와 초기화 시 actuator_forcelimited 확인은 추가하지 않았다.
기존 MotorParameters·ControllerParameters의 검증 및 JSON/검사 도구는 유지한다.

tests/test_motors.py에 TENDON 설정과 effort_limit=None의 생성 거부 검사를 추가했다.
현재 기본 JOINT 설정의 실제 PD·토크 제한 동작도 기존 검사를 재사용해 확인한다.
추가한 두 검사와 기존 모터 물리값/PD 적용·220개 토크 사례·기본 지연·HOME 초기 상태 검사를 묶어 **관련 테스트 6개 모두 통과**했다.
검사 함수의 AST도 wirlwind와 대조해 오류 메시지의 프로젝트 이름을 제외한 로직이 같은지 확인했다.
이 변경은 HOME 자세의 균형 문제를 해결하는 수정이 아니며 위의 HOME 실패 기록은 그대로 유효하다.
